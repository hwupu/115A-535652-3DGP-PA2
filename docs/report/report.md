## 1. Use of AI Tools

Puzzle Master is a third person adventure in which a witch frees five corrupted guardians, collects the items they drop and solves five puzzles before a five minute timer runs out. The main AI tool was Claude Code running Claude Opus 5.5, an AI agent that works in the terminal with direct access to the project folder, git, the GitHub command line tool, the batch mode of Unity and the Python interface of Blender. As in the first assignment, the developer acted as Product Owner as well as asset, scene and sound designer, while the AI agent acted as Scrum Master and then as programming assistant.

The AI agent wrote all C# code of the game, which consists of 46 gameplay scripts with about 3,500 lines and about 3,400 lines of Editor tooling that builds the greybox scene, links every component and checks the wiring of the scene and all prefabs. Because the developer only had to run one menu command per sprint and then play test against a checklist, scene integration never became a bottleneck. The AI agent also wrote a Blender script that derives the new melee swing animation of the witch from her existing clips. Every design decision was recorded as an Architecture Decision Record, fourteen in total, and every significant interaction was summarised in a prompt log ⟦final count⟧ entries long.

The biggest change from the first assignment was reuse. The tooling, the process documents and the lessons of the first project, such as code that fails loudly when a reference is missing and verification inside a copy of the project, were ported in the first session, so the second project started where the first one had ended. The AI agent also read the specification more carefully than a quick skim would. It found a second, conflicting marking scheme hidden inside the concept figures and asked which one counts instead of silently choosing one. In other places the developer improved on the options of the AI agent. Asked whether the player should have health, the developer chose health that is tracked in the background with the death rule kept as a single commented line, so that both interpretations of the specification can be shown to the TA. This "demo toggle" pattern became a project convention.

The limitations were the same as before, and the AI agent cannot see or play the game, so feel and appearance always depended on the play tests of the developer. Some problems came from the AI agent itself. A documentation file written by an earlier AI agent stated a wrong export scale and produced a model one hundred times too small, a test passed only because the animation it checked was not bound at all, and an attempt to keep world labels sharp under the blur effect cost many rounds before the developer decided that it was not worth the extra camera and had it reverted.

AI output was therefore never accepted on trust. Every change was compiled by Unity in batch mode inside a copy on write clone of the project, so the open Editor was never disturbed, and every setup script was run twice to prove that the second run changed nothing. Throwaway test scripts drove the built game without graphics and checked 15 combat behaviours and 30 puzzle and minimap behaviours before the developer touched anything. These end to end tests found a real bug that reading the code had missed, because the message that the final gate is open was replaced by an earlier message because of the order in which objects were enabled. The AI agent also rendered frames and screenshots and inspected them, which caught a missing sword and colours that clipped to white.

## 2. Adoption of Scrum

Scrum was adapted to a solo project in the same way as in the first assignment. All artifacts lived in the repository, namely a product backlog with a priority and the rubric marks of each item, a Definition of Done, a traceability matrix from every rubric line to its backlog items, and one document per sprint with the goal, a daily log, the review and the retrospective. GitHub Issues, milestones and a Project board mirrored the backlog, and every commit message names its backlog item and issue, as shown in Figure 2. Story points, which had lost their meaning in the first project, were dropped from the start, and a one week buffer for the build and this report was planned in from the beginning.

Sprint 0 answered fifteen product questions in one round and produced the backlog, the decision records and the plan. Sprint 1 delivered a walking skeleton with movement, the camera, the timer and the game states. Sprint 2 delivered monsters that patrol and cast spells, the melee attack, life bars, recovery and item drops. Sprint 3 delivered the five puzzles, the completion logic and the minimap, which made the game feature complete. Sprint 4 added the background music, the Hero's Journey story texts, the theme and the preparation for the demonstration, including cheat sheets and comments in the code that mark where each rubric item is implemented. ⟦Final sprint outcome and build.⟧

Each review was a play test against a checklist mapped to the rubric, and the traceability matrix showed after every sprint how many of the 100 marks were verified, rising from 55 after Sprint 2 to 90 after Sprint 3 and 95 after the music. The retrospectives produced concrete changes. In Sprint 2 the developer mistook greybox markers for items, so the next sprint gave every puzzle site a floating label, and the confusion did not return. The backlog also made scope decisions explicit. Art work was pulled forward while Sprint 3 was paused, and a polish item without rubric marks was dropped on purpose. The main challenge was pace. The plan assumed sprints of about five days from November, but with the tooling of the first project Sprints 0 to 3 were completed on the first day, so the plan had to be refined at every sprint planning rather than followed.

## 3. Reflection

The second assignment went much more smoothly than the first. Most of the problems of PA1 had already been found and solved, so the workflow between the developer and the AI agent was established from the very first day, and the time it saved could be spent on the game itself.

The difference was clearest in the daily work. The setup scripts, the checks inside a copy of the project and the play test checklists were carried over from PA1, so each sprint followed a familiar rhythm of planning, building, testing and review instead of a search for the next unexpected problem.

The game also became more meaningful. The puzzles give the player a clear goal and a purpose, since every item collected leads one step closer to the final gate. The monsters now walk their patrol routes and attack with spells, which makes the world feel far more active and alive than before.

In conclusion, the effort spent on troubleshooting the workflow in the first assignment paid off in the second, and it allowed this project to focus on giving the game a purpose and a living world.
